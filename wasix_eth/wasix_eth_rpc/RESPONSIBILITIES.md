### Updated RPC Responsibilities & Data Sourcing

This document outlines the responsibilities of the RPC calls in the `wasix_eth_rpc` crate and details where they retrieve their information from, based on the `wasix_eth_storage` table structure.

---

### 1. Ethereum Standard RPC (`eth_*`)

These calls provide standard interaction with the blockchain state, blocks, and transactions.

#### `eth_getBlockByNumber` / `eth_getBlockByHash`
- **Responsibility**: Returns information about a block by its number or hash.
- **Data Source**:
    - `Headers`: To get the block's metadata (timestamp, roots, etc.).
    - `BlockBodies`: To get the list of transactions and ommers.
    - `CanonicalHeads` / `HeaderNumbers`: To resolve block numbers to hashes or vice-versa.
- **Why**: `Headers` and `BlockBodies` are separated to optimize synchronization and disk space.

#### `eth_getBlockTransactionCountByNumber` / `eth_getBlockTransactionCountByHash`
- **Responsibility**: Returns the number of transactions in a block.
- **Data Source**:
    - `BlockBodies`: Contains the transaction list for each block.
- **Why**: Transaction counts are derived directly from the block body data.

#### `eth_getTransactionByHash`
- **Responsibility**: Returns the information about a transaction requested by transaction hash.
- **Data Source**:
    - `Transactions`: Direct point lookup of the transaction data.
    - `TransactionLookup`: To find which block contains the transaction (used to populate block hash/number in the response).
- **Why**: `Transactions` table allows O(1) access by hash, avoiding the need to scan every block body.

#### `eth_getTransactionReceipt`
- **Responsibility**: Returns the receipt of a transaction by transaction hash.
- **Data Source**:
    - `Receipts`: Stores post-execution data like logs and status.
    - `TransactionLookup`: To find the block context.
- **Why**: Receipts are only generated after execution and are stored separately to facilitate fast lookup of event logs.

#### `eth_getBalance` / `eth_getTransactionCount` (Nonce)
- **Responsibility**: Returns the balance or nonce of an account.
- **Data Source**:
    - `Accounts`: Provides the current state (balance/nonce) of an address.
    - `AccountChangeSets`: (If a historical `block_id` is provided) To "unwind" the state back to a previous block.
- **Why**: Using the `Accounts` flat state provides O(1) access. If historical data is needed, we use `ChangeSets` to revert rather than storing a full trie for every block.

#### `eth_getCode`
- **Responsibility**: Returns the bytecode of a contract.
- **Data Source**:
    - `Accounts`: To find the `code_hash` for the address.
    - `Bytecodes`: To get the actual bytes using that `code_hash`.
- **Why**: De-duplication. Many contracts share the same code; storing it once in `Bytecodes` saves significant space.

#### `eth_getStorageAt`
- **Responsibility**: Returns the value from a storage slot at a given address.
- **Data Source**:
    - `Storages`: Direct lookup using `(Address, SlotHash)`.
    - `StorageChangeSets`: (If historical) To revert changes to previous values.
- **Why**: Direct indexing in `Storages` avoids the overhead of walking the Merkle Patricia Trie for every request.

#### `eth_getLogs`
- **Responsibility**: Returns an array of all logs matching a given filter object.
- **Data Source**:
    - `Receipts`: Contains the logs generated by transaction execution.
- **Why**: Logs are the primary way for DApps to monitor state changes.

#### `eth_call` / `eth_estimateGas`
- **Responsibility**: Executes a new message call (or estimate gas) immediately without creating a transaction on the block chain.
- **Data Source**:
    - `Accounts` / `Storages` / `Bytecodes`: To provide the state for the EVM execution.
- **Why**: These require a full execution environment but do not modify the state.

#### `eth_gasPrice` / `eth_blobBaseFee` / `eth_maxPriorityFeePerGas`
- **Responsibility**: Returns current fee information for the network.
- **Data Source**:
    - `Headers`: Fee data (like base fee) is derived from recent block headers.
    - `Metadata`: For static configuration or network defaults.

#### `eth_sendTransaction` / `eth_sendRawTransaction`
- **Responsibility**: Submits a transaction to the network.
- **Data Source**:
    - `Mempool` (Memory): New transactions are first validated and placed in the mempool before being included in a block.

### 2. Engine API (`engine_*`)

Used by Consensus Clients (like Lighthouse or Prysm) to drive the execution engine.

#### `engine_forkchoiceUpdatedV1/V2/V3/V4`
- **Responsibility**: Updates the engine's view of the chain head, safe, and finalized blocks.
- **Data Source**:
    - `Forkchoice`: Stores the updated hashes for head, safe, and finalized blocks.
- **Why**: This table acts as the "pointer" to the current canonical chain.

#### `engine_getPayloadV1/V2`
- **Responsibility**: Retrieves an execution payload prepared during a previous `forkchoiceUpdated` call.
- **Data Source**:
    - `Payloads`: Temporary storage for blocks and receipts generated during the building process.
- **Why**: Separation from the main chain data ensures that "uncommitted" blocks aren't mixed with the canonical chain until signaled.

#### `engine_newPayloadV1/V2/V3/V4`
- **Responsibility**: Validates and potentially executes a new block received from the consensus layer.
- **Data Source**:
    - `Headers` / `BlockBodies`: To persist the new block.
    - `HashedState` / `TrieNodes`: To calculate and verify the state root.
    - `AccountChangeSets` / `StorageChangeSets`: To record changes for potential future reorgs.

#### `engine_getPayloadBodiesByHashV1` / `engine_getPayloadBodiesByRangeV1`
- **Responsibility**: Returns block bodies for the consensus client.
- **Data Source**:
    - `BlockBodies`: Contains the transactions and withdrawals.

#### `engine_exchangeCapabilities` / `engine_exchangeTransitionConfigurationV1`
- **Responsibility**: Negotiates features and settings between the Execution and Consensus clients.
- **Data Source**:
    - `Metadata` or Static configuration.

### 3. Debug API (`debug_*`)

Used for inspection and troubleshooting.

#### `debug_getMempool`
- **Responsibility**: Returns all transactions currently in the mempool.
- **Data Source**:
    - `Mempool` (Memory): In-memory storage for pending transactions.

#### `debug_getRawBlock` / `debug_getRawHeader` / `debug_getRawTransaction` / `debug_getRawReceipts`
- **Responsibility**: Returns the RLP-encoded bytes of the requested data.
- **Data Source**:
    - `Headers`, `BlockBodies`, `Transactions`, `Receipts`.
- **Why**: Useful for tools that need the exact byte representation rather than decoded JSON.

### 4. Networking & Node State

#### `eth_syncing`
- **Responsibility**: Returns an object with data about the sync status or false.
- **Data Source**:
    - `Metadata`: Stores the highest seen block or sync progress.
    - `Forkchoice`: To compare current head with the target.

#### `eth_accounts` / `eth_sign` / `eth_signTransaction`
- **Responsibility**: Manages node-side accounts and signing.
- **Data Source**:
    - Key storage (typically external to the main DB tables or in a secured `Metadata` section).

#### `eth_chainId` / `eth_mining` / `eth_blockNumber`
- **Responsibility**: Returns basic node and network state.
- **Data Source**:
    - `Metadata`: For `chain_id`.
    - `CanonicalHeads`: For the current `block_number`.
